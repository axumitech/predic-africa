## Premier module : Ledger / portefeuille simulé

Unité : crédit fictif entier, pas de devise réelle. Mise bornée par les contrôleurs, cote entière en centièmes ; retour `intdiv(stake * odds, 100)` (arrondi inférieur). Compte utilisateur non négatif ; contrepartie simulation autorisée négative. Le Ledger ne fixe pas la limite HTTP de 1 000 000, car les gains peuvent la dépasser.

Changements : verrou utilisateur désormais assuré dans Ledger ; comptes verrouillés dans leur ordre d’identifiant ; référence relue sous verrou après acquisition des comptes ; sens vérifié sur l’écriture utilisateur sans modifier les empreintes historiques ; gardes BIGINT avant calcul SQL. Les verrouillages des contrôleurs restent compatibles. Le compte simulation commun sérialise les écritures ; ne pas en déduire une capacité de charge.

`php artisan ledger:reconcile` est une commande en lecture seule : comparaison de chaque solde à son journal, détection des soldes utilisateurs négatifs, transactions absentes du journal, paires incomplètes, comptes non distincts et sommes non nulles. Retour 0 si aucun écart, 1 sinon. Exécuter sans écritures concurrentes ou sur une copie cohérente : les deux requêtes ne constituent pas un instantané commun. Aucune réparation automatique. Ce contrôle n’est pas un audit de toutes les correspondances position/gain, ni du contenu métier de chaque écriture. Non exécuté sur la base existante dans ce lot ; testé sur bases isolées. Corriger un écart exige d’en déterminer la cause et d’enregistrer une compensation traçable ; aucune API de compensation ajoutée ici.

Pas de migration, dépendance ou changement des règles de paiement. Retour arrière : retirer la commande, son test et les changements de Ledger ; aucun rétablissement de données requis. Les écritures historiques restent intactes.

## Lot 2 — Trading / Settlement

### Rôle, interfaces et invariants

Trading possède les positions à cote fixe, dépend d’Identity, Markets et Ledger. `PlacePosition::place` réalise la mise atomique ; le contrôleur HTTP conserve la validation d’entrée. Settlement orchestre l’état final du marché et des positions avec Markets, Trading, Ledger et Notifications ; `ResolveMarket::resolve` est interne et son contrôleur vérifie le rôle administrateur. Deux classes d’opération simples permettent d’exercer exactement la logique HTTP depuis plusieurs processus ; aucune couche repository ou dépendance nouvelle.

Transitions : marché open avec échéance future → nouvelle position open. À l’échéance exacte, nouvelle mise refusée, résolution yes/no permise. Une annulation void est permise avant/après échéance ; toutes les mises sont remboursées, quelle que soit l’issue. Résolution yes/no : gagnants crédités selon la cote mémorisée, perdants sans crédit. État final rejouable seulement pour le même résultat et sans position encore ouverte ; la première source reste conservée. Marché pending/rejected non réglable. La suspension interdit les nouvelles mises mais n’empêche pas le versement des positions engagées.

### Défauts et corrections

- **Haute — interblocage d’ordre utilisateur/compte** : ancienne boucle Settlement pouvant attendre un autre utilisateur après acquisition du compte simulation. Désormais tous les participants sont verrouillés en ordre croissant avant le premier transfert.
- **Haute — interblocage réellement reproduit sur InnoDB** : malgré ce premier correctif, le scénario imposé a échoué et `SHOW ENGINE INNODB STATUS` a montré une résolution tenant le verrou d’index `positions_market_id_status_user_id_index` (notamment son intervalle supremum), attendant un utilisateur ; sa mise sur un autre marché tenait cet utilisateur et attendait l’insertion dans cet intervalle. InnoDB a annulé la résolution et la reprise automatique masquait le conflit aux scénarios plus simples. Retrait du `FOR UPDATE` de plage sur positions : le verrou préalable du marché sérialise déjà tous les chemins applicatifs qui écrivent ses positions. Le même scénario passe ensuite sans reprise transactionnelle.
- **Haute — débit orphelin** : le rejeu d’une référence de mise dont la position avait disparu recréait une position même sur marché terminé. Désormais refus explicite et rapprochement requis ; le rejeu normal après remboursement/résolution reste sans effet et une position liée incohérente est refusée.
- **Haute — données enregistrées non contrôlées au paiement** : une cote hors bornes ou un payout altéré pouvait être utilisé. `FixedOdds` centralise les règles déjà documentées ; Settlement vérifie le payout mémorisé, l’issue et la correspondance de la position avec sa transaction de mise, son empreinte et l’écriture utilisateur négative. Les données incohérentes provoquent un refus atomique, pas une réparation silencieuse.
- **Moyenne — états partiels ignorés** : marché ouvert avec positions déjà traitées, marché terminé avec positions ouvertes ou statut/résultat contradictoires désormais refusés. Source réduite aux espaces refusée.
- **Moyenne — suspension lue trop tôt** : la mise relit l’utilisateur sous verrou dans l’opération métier ; elle ne dépend plus seulement de l’objet authentifié lu par le middleware.

Fichiers : `app/Modules/Trading/{PlacePosition,FixedOdds}.php`, `app/Modules/Settlement/ResolveMarket.php` et les deux contrôleurs HTTP. La transaction englobante, les crédits fictifs, les règles de gain, les références historiques et les trois tentatives SQL sont conservés. Aucun événement différé ajouté aux écritures financières.

## Lot 3 — Identity et autorisations

### Cartographie et contrôle des accès

Périmètre relu : routes web, bootstrap et middleware, IdentityController, modèle User et factory, config auth/session, contrôleurs de lecture, support, marchés, paiements, administration du pipeline et règlement ; commande serveur d’attribution admin, champs du profil React et tests existants. L’authentification utilise le guard web par session Laravel, sans API token ni OAuth. Les pages publiques et deux API de lecture simulée sont intentionnellement accessibles aux invités. Les mutations restent dans le groupe web avec protection native PreventRequestForgery ; pas d’exception CSRF ajoutée.

Identity possède users et la politique de session ; ses opérations restent inscription/connexion/déconnexion/profil/suspension via HTTP. La création de compte et du portefeuille zéro demeure atomique. L’écriture du profil et l’invalidation logique des sessions partagent une transaction utilisateur. Les contrôles d’accès sont synchrones ; aucune file d’attente ne doit décider ultérieurement d’une permission. Une relecture utilisateur supplémentaire par requête authentifiée du groupe web évite de fonder les autorisations sur un objet conservé en mémoire.

### Défauts établis et changements

- **Haute — sessions persistantes après changement de mot de passe.** Le test de rejeu d’une ancienne session rendait 200 sur /wallet avant correction. Migration additive auth_version ; incrément atomique lors du changement, rotation du remember_token, nouvelle session/CSRF pour le client courant et refus des autres sessions à leur prochaine requête. Vérifié ensuite avec deux clients HTTP à cookies distincts et sessions stockées en base.
- **Haute — réactivation restaurant les anciennes sessions.** Ancien middleware ne testait que suspended. Une session conservée sans requête pendant la suspension retrouvait l’accès après réactivation (test initial 200 au lieu de 401). Une suspension effective incrémente désormais auth_version ; une répétition ne l’incrémente pas ; la réactivation ne remet jamais le compteur à zéro. Reconnexion explicite requise.
- **Haute — données partagées d’un compte suspendu sur pages publiques.** ActiveAccount ne s’appliquait qu’aux routes privées, alors que HandleInertiaRequests partageait auth/balance/unread sur toutes les pages. Le contrôle précède maintenant le partage Inertia dans le groupe web entier ; une session suspendue est vidée avant la réponse 403 et n’y expose pas ces propriétés. Une visite suivante est anonyme.
- **Moyenne — contrôle sur objet utilisateur conservé et dispersion des règles.** Une rétrogradation en base n’était pas reflétée dans les tests conservant l’objet authentifié (200 sur /admin). Ce test ne démontre pas à lui seul un exploit sous PHP-FPM, qui recharge normalement le guard par requête. Le middleware impose maintenant une relecture explicite. Gates `admin`, `view-market`, `access-ticket` communes aux lectures et mutations ; aucun Gate::before accordant tous les droits à un admin. Rôles inconnus refusés à la connexion et sur session existante.
- **Moyenne — vérification du mot de passe du profil hors verrou.** Vérification de Hash::check sur la ligne utilisateur verrouillée ; champs modifiables explicitement affectés, gestion des collisions SQL d’e-mail et effacement de email_verified_at si e-mail changé. Aucun e-mail envoyé ni nouvelle obligation de vérification activée. Les valeurs par défaut de l’utilisateur inscrit sont relues avant connexion.
- **Moyenne — suspension de cible sans relecture de l’acteur dans la transaction.** Acteur et cible verrouillés dans l’ordre des identifiants ; droits de l’acteur relus après attente. Une suspension révoque aussi le remember_token ; auto-suspension interdite. Le contrôleur de paiement vérifie désormais la suspension sur sa ligne verrouillée, comme Trading.
- **Moyenne — tentatives réparties entre IP.** Limite login historique par IP conservée (six/minute), complétée par une limite dix/minute pour l’e-mail, avec clé hashée et insensible à sa casse pour le compteur. Aucun nom d’utilisateur ou e-mail brut ajouté aux logs.
- **Moyenne — quotas partagés entre mutations et génération.** Un test de matrice d’autorisations a révélé un HTTP 429 avant le contrôle du rôle parce que le compteur trois/minute de génération réutilisait celui des mutations précédentes. Préfixe dédié ajouté pour la génération, conservant la limite globale de trente mutations/minute.
- Durcissement des réponses : `private, no-store` pour pages Inertia et erreurs ; signal Inertia clearHistory sur logout/révocation/changement de mot de passe. Ne pas assimiler ce signal à une purge certifiée de caches ou de l’historique déjà affiché.
